# Формат `.familytree`, версия 1

`.familytree` — обычная база SQLite 3 с явно описанной схемой. Один файл содержит проект, людей, связи, события и полные байты вложений. Для чтения данных на другой платформе нужны SQLite и реализация этой схемы; Swift, SwiftUI и macOS для самого формата не требуются. Готового приложения для Windows пока нет.

## Определение формата

| Поле | Значение |
| --- | --- |
| Заголовок файла | Стандартный `SQLite format 3` |
| `PRAGMA application_id` | `1179931205`, ASCII `FTRE` |
| `PRAGMA user_version` | `1` |
| `project.format_version` | `1`; должен совпадать с `user_version` |

Приложение проверяет идентификатор, версию, `PRAGMA quick_check` и смысловую целостность проекта. Неизвестная версия, чужая база или повреждённый документ вызывают ошибку. Сохранение поверх такого файла запрещено. Миграций из других версий пока нет; при изменении схемы требуется новая версия и отдельная миграция.

## Общие правила

- Идентификаторы — UUID в текстовой форме `XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX`. Записываются прописными латинскими буквами. Ссылки на записи используют UUID, а не порядок строк.
- Текст — Unicode. Пустая строка означает, что текстовое значение не заполнено. Неизвестные необязательные UUID хранятся как SQL `NULL`.
- `sort_index` — целое число, сохраняющее порядок записей соответствующего массива. Чтение выполняется с `ORDER BY sort_index`.
- Булевы значения — целые `0` и `1`.
- `created_at` и `modified_at` — `REAL`: число секунд с **2001-01-01 00:00:00 UTC**. Для Unix time прибавьте `978307200`. Такая запись сохраняет точность `Foundation.Date` без изменения значения при повторном чтении.
- Даты рождения, смерти и событий — исходные текстовые строки. Допустимы точные и неполные даты, приблизительные формулировки и диапазоны; формат не превращает «около 1932» в фиктивную точную дату.

## Таблицы

### `project`

Одна строка: `singleton INTEGER PRIMARY KEY` со значением `1`; `id TEXT`, `title TEXT`, `created_at REAL`, `modified_at REAL`, `root_person_id TEXT NULL`, `format_version INTEGER`.

`root_person_id` — выбранный главный человек дерева. При наличии должен ссылаться на существующую запись `people`.

### `people`

`id TEXT PRIMARY KEY`, `sort_index INTEGER UNIQUE`, `given_name TEXT`, `patronymic TEXT`, `family_name TEXT`, `maiden_name TEXT`, `gender TEXT`, `birth_date TEXT`, `death_date TEXT`, `is_deceased INTEGER`, `birth_place TEXT`, `occupation TEXT`, `biography TEXT`, `photo_id TEXT NULL`, `is_favorite INTEGER`.

`gender`: `male`, `female`, `unspecified`. `photo_id` ссылается на вложение той же карточки человека. Имена, биографии и неопределённые даты сохраняются без потери исходного текста.

### `relationships`

`id TEXT PRIMARY KEY`, `sort_index INTEGER UNIQUE`, `from_id TEXT`, `to_id TEXT`, `kind TEXT`.

| `kind` | Смысл направления |
| --- | --- |
| `parent` | `from_id` — родитель, `to_id` — ребёнок |
| `adoptiveParent` | `from_id` — приёмный родитель, `to_id` — ребёнок |
| `partner` | Симметричная связь партнёров; порядок концов не имеет значения |

Проверка запрещает ссылки на отсутствующих людей, связь с собой, семантические дубликаты и циклы происхождения. Циклы проверяются по совокупности обычных и приёмных родительских связей. Несколько партнёрств и повторное появление общего предка в разных ветвях допускаются.

### `events`

`id TEXT PRIMARY KEY`, `sort_index INTEGER UNIQUE`, `person_id TEXT`, `kind TEXT`, `title TEXT`, `date TEXT`, `place TEXT`, `notes TEXT`.

`kind`: `birth`, `marriage`, `residence`, `education`, `work`, `death`, `other`. Событие принадлежит одному человеку. Источники и пояснения можно записать в `notes`; отдельной модели архивных источников и цитат в версии 1 нет.

### `attachments`

`id TEXT PRIMARY KEY`, `sort_index INTEGER UNIQUE`, `person_id TEXT`, `filename TEXT`, `mime_type TEXT`, `data BLOB`, `caption TEXT`.

`data` содержит исходные байты целиком. Пустое вложение — BLOB длины ноль, не SQL `NULL`. `filename` служит отображаемым именем, а не внешним путём: приложение не загружает файлы с диска по сохранённому имени. Перенос `.familytree` переносит и вложения.

Внешние ключи SQLite связывают `relationships`, `events` и `attachments` с `people`. Дополнительно приложение проверяет все ссылки, уникальность UUID внутри каждой таблицы, главного человека и принадлежность фотографии.

## Сохранение и резервная копия

1. Проверяется проект в памяти; существующий целевой файл также полностью читается и проверяется.
2. Рядом создаётся временная база. Все таблицы и записи записываются в одной транзакции с `journal_mode=DELETE` и `synchronous=FULL`.
3. Временная база повторно открывается и проверяется.
4. Если исходный файл существует, SQLite Backup API создаёт его согласованную копию. Она атомарно заменяет `<имя>.familytree.backup`.
5. Проверенная новая база атомарно заменяет основной файл переименованием в том же каталоге. Временные файлы убираются; выполняется попытка синхронизировать каталог.

При ошибке до последнего переименования основной файл остаётся прежним. `.backup` содержит одну предыдущую сохранённую версию, а не полную историю правок. На первый успешный save резервной копии ещё нет. Для независимого архива следует копировать проект в другое место или использовать системное резервное копирование.

Версия 1 предполагает одного писателя. Одновременное редактирование одного файла разными процессами и согласование конфликтов облачной синхронизации не реализованы. База не зашифрована. При больших коллекциях вложений полная перезапись требует дополнительного свободного места и времени.

## GEDCOM

GEDCOM — отдельный формат обмена, не полный формат сохранения приложения. Экспорт `.ged` не содержит бинарных вложений и не обещает сохранить все особенности нативного проекта. Для полной копии используйте `.familytree`; конкретные ограничения обмена перечислены в [сравнении возможностей](FAMYTALE.md).
